## 打底：先补 3 个 vLLM 概念（不认识，下面几节会读不懂）

下面几节到处都是这几个词，先一次性说清：

| 概念 | 大白话 | 主要在哪些节出现 |
|------|--------|-----------------|
| **prefill / decode** | 一次回答分两相：**prefill** = 把输入"读懂"成 KV 缓存（一次性、吃算力）；**decode** = 一个字一个字往外吐（连续、吃访存）。**算力峰值只看 prefill** | A1（output_len=1）、A2 | 
| **KV cache / prefix caching** | 把已算过的历史 token 缓存在显存，下次同前缀不重算；prefix caching = 跨请求复用这份缓存 | A2 ⑤、A3（关缓存）、A4 |
| **图捕获（capture）** | 提前把固定 batch 形状的算子编译成加速图，跑时直接套；vLLM 的 `capture_sizes` 就是预编译哪些形状。用它提速 = "图优化" | A1（eager=真/禁图）、A2/A3/A4（capture_sizes） |

> 解释原则：本文的"为什么"都立在这 3 个概念 + [全局词典](../README.md#L41) 之上；看不明白就回这里对一眼。

## 0. 先记住一条贯穿四门的总原则：所有配置都在服务「可复现 + fail-closed」

新人最容易困惑：为什么 sampling 全是 `temperature: 0.0`、还带一堆 seed？

- **要可复现**：同一份配置跑两次要拿到同一批请求、近乎同样的输出，B0/B1 才能逐字节对账。所以 `temperature=0`、`client_seed=0`、`engine_seed=0`、`PYTHONHASHSEED=0`、确定性合成数据，全是为了「两次能对得上」。
- **要 fail-closed**：配置里出现 `schema.yaml` 白名单之外的字段，直接拒绝起不来。宁可爆错，不许"这次算了"。
- **要贴硬件**：所有 cell 都 `tensor/pipeline/data/expert_parallel=1`、`VLLM_TARGET_DEVICE=npu`，因为验收对象就一台 Atlas 910B2（*详见 [CONTEXT.md](../../CONTEXT.md) 的隐私边界——不写具体机器*）。

下面按 A1 → A2 → A3 → A4 逐个拆。

## 1. A1 算力口径 —— 「这块卡，你真发挥满了吗？」

### 需求 / 目标
商业上它是**能不能在交付书上写"达到算力口径"**的硬指标。它不关心"快不快"，只回答一件事：**理论的峰值算力，实际用出来几成（MFU≥90%）**。这决定你敢不敢对外承诺算力、以及排查"为什么我比别人慢"时先查硬件利用率。

### 判定
- 主形状 `4096×8→1` 的 **MFU ≥ 90%**；
- msprof 对账误差 ≤ 3%；
- **图捕获 = 0**（接住这个才算真算力，见下）。

### 为什么这么配（逐项）

| 配置 | 为什么这么设 | 改了会怎样 |
|------|-------------|-----------|
| `mode: closed-loop` | 算力要看"满负荷连续算"，闭环保证每一刻都在算，而不是随机到达的模拟 | 换 poisson 就变成"扛并发"，量不到真正的算力上界 |
| 主形状 `4096×8→1` | 接近典型大批次满算的形状，是 MFU 的主判据 | —— |
| 辅形状 `1024×32` / `8192×4` | 换 batch 宽度与 sequence 长度，验证 FLOPs 计数/单调性在不同形状下仍成立 | —— |
| `output_len: 1` + `max_tokens: 1` | 只算 **prefill** 算力（decode 主要是访存、不计入 FLOPs 峰值），MFU 口径统一按 prefill | 输出变长会混入 decode，MFU 失真 |
| `ignore_eos: true` | 强制不中途停，保证每问都产生那 1 个 unit，采样可复现 | eos 提前打断则请求体不可比 |
| `compile_mode: none` + `enforce_eager: true` + `cudagraph_mode: none` | 让 **图捕获=0**：MFU 要看"裸算力"，不许靠图优化兜底掩盖真实算力不足 | 开了图优化，等于"考试作弊"，AFU 不再诚实地反映硬件 |
| `enable_prefix_caching: false` | 复用前缀会少算 FLOPs，破坏算力口径 | 开了复用，FLOPs 被低估 |
| 固定 FP16 | 峰值算力按张量单元的 FP16 定义；W8A8 是降精度优化，不做算力峰值口径 | —— |

## 2. A2 SLO 组 —— 「网上同时来一堆请求，你回得快还稳吗？」

### 需求 / 目标
A2 是**在线并发**的压力面试：在「延迟可接受」的前提下，系统能扛住多大的并发？它比 A1 多了两个层次的要求——**既要快（SLO），又要对（质量）**。5 个 cell 就是 5 种真实业务形态：对话、工具、推理、结构化、长上下文。

### 判定
- 找到**最大合规点 b0_max**：所有 SLO 都满足的最大吞吐（完成率≥99%、error_rate≤0.1%、TTFT/TPOT p99 阈值）；
- 正式负载取 `0.70 × b0_max`——留裕量的「共同负载」下再量 TTFT/TPOT 和质量；
- 质量门禁：concept 答得对不对（工具/推理/结构化各有 oracle）。

### 为什么这么配

**① 用容量扫描 + 0.70×，而不是直接压满**
`mode: poisson` + `rates` 升序扫描 → 求 b0_max → `0.70×` 做正式负载。Why：**扫描是在找上界**（证明能到哪），**0.70× 是在证明"在留了裕量的现实负载下依然合规"**。直接压满既证明不了日常可用性，还容易把服务打崩导致没法量到稳态。

**② 5 种 cell 为什么 dataset 各不同**
每个 cell 对准一种真实业务：dialogue 用 ShareGPT 多轮、tool 用 BFCL 真实工具、reason 用 GSM8K 抽答案、struct 用 JSONSchema 逐 case 发 schema、long 用长文本。Why：**质量 oracle 只能贴着真实业务判**——「结构化输出排不合法 schema」这种结论，用假数据是验不出来的。

**③ max_num_seqs 为什么不同**
dialogue=32、reason/tool/struct=16、long=4。Why：**尾生成越短、越可并行的越能高并发**（对话多轮、首 token 快可多排）；reason/struct 是长生成，并发调低避免排队尾部长尾；long 是超长输入，低并发防内存爆。改大了，p99 尾延迟会因队列变长而爆炸。

**④ SLO 阈值为什么按输入长度放宽（long）**
对话的 `TTFT p99≤4000ms`，但 long 的 8192/16384 档放宽到 16000/32000ms。Why：**TTFT 正比于 prefill 量**，16k 字长输入的 prefill 天然比对话慢，拿一个数卡所有任务是不公平的——这也是"专家"要懂的关键。

**⑤ `enable_prefix_caching` 有开有关**
dialogue/tool 开 `true`（多轮/同前缀复用），reason/struct/long 关 `false`。Why：**A2 要量真实学力**。开着缓存测对话没问题（那正是它的实际行为），但对 struct/long 若开缓存会隐藏真实 prefill 成本，故关掉。

**⑥ `structured_outputs_backend: xgrammar` 且禁止 auto**
struct 是逐 case 发 JSON Schema。Why：backend=auto 会"挑一个没准的"，不可复现；**必须显式钉 xgrammar** 才能批量判 schema 合法率。

## 3. A3 窗口稳定 —— 「一口气读 32k 字、跑半个钟，会不会越跑越慢？」

### 需求 / 目标
A1/A2 都是**瞬时**能力，A3 验的是**长时间尺度**的稳定性：长文本下连续跑 30 分钟（6×5 分钟窗口），吞吐不抖、延迟不漂、零失败。市场意义=敢不敢承诺"长会话/长文档场景挂着不掉链子"。

### 判定
窗口吞吐 **CV≤5%**、中位漂移 **≤10%**、p99 **≤20%**、**0 失败**。

### 为什么这么配

| 配置 | 为什么这么设 |
|------|-------------|
| `closed-loop` + `concurrency: 1` + `max_num_seqs: 1` + `capture_sizes: [1]` | **串行单请求打满**，排除并发干扰，只测"一个长请求自身稳不稳"。加并发就把"稳定问题"和"调度抢占"搅在一起，不好归因 |
| 总上下文 `32768` = 输入 `30720` + 输出 `2048` | 贴满 `max_model_len` 的**最坏压力**，测的就是极限长文本 |
| `6 × window_s 300` | 分成 6 个 5 分钟窗口看：CV/漂移本是"分段看波动"，不切窗就没法量化"抖不抖" |
| `ignore_eos: true` + `max_tokens: 2048` | 强制输出固定 2048，输出不被随机截断，窗口之间才可比 |
| `enable_prefix_caching: false` | 缓存前缀会掩盖每窗真实算力，稳定结论失真 |
| `enable_chunked_prefill: true` | 30720 prefill 不分块会**内存溢出**，这是"依赖分块的正常能力项"，与 A2 里刻意关闭复用是两回事 |

> 辨析：A2 关 prefix cache 是"保真实学力"，A3 开 chunked prefill 是"必须分块才能跑"，两者目的不同，别混。

## 4. A4 多租户成本 —— 「4 个客户挤一台，谁也别被欺负？最后每百万 token 多少钱？」

### 需求 / 目标
A4 验两大件事：**①公平/隔离**——4 个按份额付钱的租户共享一台服务，谁都不该被"欺负"；**②成本**——每百万 token 到底多少钱，且所有租户价格口径一致。商业意义=敢不敢对外卖"多租户共享"并且定价公道。

### 判定
- **公平性**：Jain≥0.90、份额偏差≤10%（四租户各 25%）；
- **隔离**：相对隔离比值 **≤1.25×**（单租户独占延迟 vs 混载延迟）；
- **容量**：b0_max + `0.70×` 正式负载；
- **成本**：统一 `÷21600h + 0.6 元/kWh + 每百万 token` 口径。

### 为什么这么配

> 本节的**结论性决策**唯一出处为 [ADR-0009](../adr/0009-a4-mt-isolation-tuning.md)（max_num_seqs 演化 + 隔离口径）；本节是给"任务专家"看的**完整推理过程**，两处一致，改动以 ADR 为准。

**① 为什么是 `max_num_seqs: 36`（= 4 租户 × per_tenant 9 = global 36）**
这是 verify15→19 真机反复校准出来的，不是拍脑袋：
- 16 并发 → KV 缓存利用率低、吞吐不足；
- 48 并发 → 高并发引发更多 prefill/decode 抢占，p99 全面升高；
- **36** → `per_tenant_concurrency` 与 `max_num_seqs` 匹配（4×9），`capture_sizes` 显式扩到 36 覆盖峰值 batch；隔离基线解除 per-tenant 限流后，单租户还能独占满 36 并发，与混载同并发天花板对比，才是公平口径（*注释缘由见 [a4-mt.yaml](../../config/vllm-xcheck/cells/a4-mt.yaml)*）。

**② `cost_len` 与 `output_cap` 为什么要分开**
- `output_cap`：单请求 `max_tokens` 上限，**防不受控**（挡长生成把你打爆）；
- `cost_len`：期望输出长度/**调度成本**，`request_rate = token_rate × share / cost_len`。
拆开才不打架：调度要按"预期多长"排班，防爆栈按"最强多长"兜底。`cost_len` 取真机实测（dialogue 13 / tool 5 / reason 2 / struct 23），否则 `request_rate×cost_len` 下份额收敛不到 25%。

**③ `isolation_token_rate` 为什么必须设**
`cost_len` 大的租户（dialogue/structured）在老配置下隔离基线请求率过低、**基线并发只有 ~17**，达不到 36 满并发 → 基线 p99 被低估 → 相对隔离假 FAIL（verify18 的 structured tpot 1.36× 就是这么来的）。该键把基线 `token_rate` 提到该租户 solo 满载 36 并发的水平，让四租户基线同为 **worst-case solo p99**，比较才对等。

**④ 延迟判定为什么用「相对隔离 ≤1.25×」而非绝对 SLO**
多租户共享下，绝对延迟本来就比单租户独占差，**拿绝对数卡各租户没意义**；真正该问的是"挤一起时比我独占时差多少"。所以改用比值——**这是比 A2 更关键的专家点**。

**⑤ 成本为什么钉「÷21600h + 0.6 元/kWh + 每百万 token」**
"划算不划算"必须唯一口径，否则租户间、机型间无法横向比较。`21600h`=生命周期年化、电费单价、按成功输出 token 计价，全部在 [cost.py](../../src/client/cost.py) 落成同一算法。
